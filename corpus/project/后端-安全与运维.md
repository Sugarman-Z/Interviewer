topic: SQL 注入防御
difficulty: 2
tags: 安全, 数据库
source: LLM 草拟·人审通过·2026-11-17

**题目**
代码评审时同事拍胸脯说：查询全走了 ORM 的预编译，SQL 注入这一页可以翻过去了。可列表接口把前端传来的排序字段直接拼进了 SQL。你同意这个结论吗？讲讲注入还能从哪些口子进来、靠什么挡住。

**追问树**
- 预编译为什么能防注入？参数和语句结构在数据库侧是怎么分开对待的？
- 表名、列名、ORDER BY 字段这些没法参数化的位置，安全的处理方式是什么？
- 有了预编译还要不要最小权限账号和 WAF？各自的兜底边界在哪？

**评分锚点**
- 5 分：能说清预编译挡住什么、挡不住什么，能指出表名列名拼接等注入面并给出纵深防御
- 3 分：知道预编译和参数化查询，但说不出哪些位置参数化不了、ORM 哪些写法会破防
- 1 分：只会答转义特殊字符或「ORM 天然安全」，把单一手段当万能药

topic: XSS 与 CSRF
difficulty: 3
tags: 安全, web
source: LLM 草拟·人审通过·2026-11-17

**题目**
评论区上线前，组里两个新人吵起来了：一个说 XSS 和 CSRF 都是伪造请求，防住一个另一个也就防住了；另一个觉得不对但说不出为什么。你来裁决：两类攻击的利用机制差在哪？各配什么防线，哪些手段对两者都管用？

**追问树**
- 存储型、反射型、DOM 型 XSS 的注入点分别在哪儿？修复位置在前端还是后端？
- CSP 上线后为什么常被迫开 unsafe-inline？改用 nonce 要动什么？
- SameSite=Lax 默认铺开后 CSRF 还剩哪些绕过路径？token 还有必要吗？

**评分锚点**
- 5 分：能分清两类攻击的信任模型（执行恶意代码与借用身份发请求），能指出 CSP、SameSite 各自的防御边界和失效条件
- 3 分：知道 XSS 要转义、CSRF 加 token，但说不出 SameSite 和 CSP 的局限与适用条件
- 1 分：把两类攻击混为一谈，或只会背「转义、加 token」两句口诀

id: bank-be-050
topic: JWT 与 OAuth2
difficulty: 3
tags: 安全, 鉴权
source: LLM 草拟·人审通过·2026-11-17

**题目**
产品要接「用微信登录」，你负责后端：第三方走 OAuth2 授权码流程，换回来的凭证你们打算用 JWT 来签发。这条链路上会出现好几种 token，讲讲每一种的生命周期：谁签发、给谁用、活多久、出事时怎么作废？

**追问树**
- 为什么先发授权码再换 token，多出的一跳防的是什么攻击？
- refresh token rotation 检测到重放时，正确的处置动作是什么？
- access token 用 JWT 自包含，和用不透明 token 查认证端点，各自牺牲了什么？

**评分锚点**
- 5 分：能说清授权码、access、refresh 三种 token 的角色与时效联动，能指出吊销难点和 rotation 防重放的处置
- 3 分：知道授权码流程的大致步骤，但说不清各 token 的时效设计和吊销代价
- 1 分：只会说 JWT 无状态、加密了就安全，几种 token 的角色分不清

id: bank-be-051
topic: 线上排查工具箱
difficulty: 2
tags: 运维, linux
source: LLM 草拟·人审通过·2026-11-17

**题目**
凌晨被告警叫醒：一台 Linux 机器上的服务响应变慢，好在还能 SSH 上去。从登录那一刻起，你会按什么顺序把 CPU、内存、磁盘、网络四条线各查一遍？每条线上用什么工具、盯哪个信号，怎么决定下一步往哪收？

**追问树**
- load average 很高但 CPU 使用率不高，瓶颈可能卡在哪类资源上？
- df 显示磁盘没满，写入却报 No space left，是什么耗尽了？怎么验证？
- 服务慢但 CPU、内存、磁盘都正常，网络这条线你会依次用什么工具查？

**评分锚点**
- 5 分：四条线各有具体工具和判断信号（如 wa 高转 iostat、连接数看 ss），能按先粗后细的顺序收敛到瓶颈
- 3 分：知道 top、free、df 等常用工具，但每条线只看总量，说不出下一步往哪收敛
- 1 分：登上去 top 一眼或干脆重启服务，没有排查路径

topic: 监控与告警治理
difficulty: 3
tags: 运维, 监控
source: LLM 草拟·人审通过·2026-11-17

**题目**
值班群里每晚滚几百条告警，大家早就集体静音，而上周两次真故障都是用户投诉才发现的。让你重构这套监控：哪些指标才配上告警，口径怎么定，才能让告警重新被人当真？

**追问树**
- 接口延迟为什么不该只看平均值？P99 和 P50 各回答什么问题？
- CPU 使用率飙到 95% 就该告警吗？什么情况下高使用率反而是健康的？
- SLO 定了 99.9% 之后，错误预算怎么和告警联动？多窗口告警解决什么问题？

**评分锚点**
- 5 分：能按症状而非原因选指标（分位数、错误率、饱和度），能说清 SLI 口径与 SLO 错误预算的联动及告警分级
- 3 分：知道延迟、CPU 等常见指标，但分不清哪些配上告警、口径该怎么定
- 1 分：只会「加个阈值告警」，认为指标和告警堆得越多越安全
